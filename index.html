THE PHOTONIC LANGUAGE

Write rules.
Explore their consequences.

A Photonic program describes how information can change and which changes can happen together.

You write the data and the rules that act on it. The runtime explores the possible results, keeping track of which information each step used. This book starts with a small program, then builds up to abstractions, arithmetic, and the Rust execution graph.

01 / PHILOSOPHY

A world of rules.

A rule names the information it needs and describes what it produces.

A configuration contains the coherences that exist together, their contents, and the environments in which their rules operate. Applying a rule produces a successor configuration. When several rules can apply, the same starting point may have several successors.

Photonic takes its physical inspiration from interactions that require their participants to be present together. The runtime tracks those participants by identity and records the derivations that support each event.

EVIDENCE
A value can reach an abstraction through rules.
That derivation can justify another rule at the original value.
01

Positive evidence

A rule applies because its inputs have support. Not can be an ordinary program-defined concept; the language gives it no intrinsic negation behavior.

02

Orderless, with multiplicity

A.B and B.A describe the same arrangement of values. A.A still contains two independent occurrences.

03

One model, many uses

Rules express conversion, classification, synchronization, and code production. A type-like abstraction is established by computation.

02 / GRAMMAR

Reading Photonic source.

Dots join values in a particle. Commas separate coherences. Brackets introduce rule inputs.

The fundamental grammar recognizes concepts, dots, commas, parenthesized groups, bracketed source contexts, and whitespace. These describe source structure. Matching, execution, and lowering behavior are explained in the following chapters.

Both .particle and .wave use this grammar. By convention, .particle holds reusable rules or data and .wave holds scripts.

FormNameSyntactic role
AConceptText delimited by punctuation or whitespace
.DotA continuation separator, as in A.B
,CommaA coherence separator, as in A, B
( … )GroupParentheses enclosing source items
[ … ]Source contextBrackets enclosing source items
Space, tab, newlineWhitespaceSeparates source items; ASCII whitespace is accepted

Read the structure before the behavior

A.B
[A] C

The first line puts A and B in one particle. The second is a rule: consume A and produce C. Parsing records the written structure; lowering turns that structure into the values and rules the runtime uses.

GRAMMAR LENS

Recognize the source items



Groups and source contexts may nest, including empty () and []. Their delimiters remain the same at every level. Rule production, scoped bodies, and the meaning of empty outputs belong to the executable interpretation.


Does whitespace replace a dot?
No. Whitespace separates source items; a dot is its own grammatical item. The executable interpretation uses that distinction when reading particle composition.

03 / INTERACTION
How coherences
split and join.


A coherence is an independently evolving context. A configuration tells you which coherences coexist.


Divergence creates multiple output coherences. Decoherence combines compatible input coherences through one joint match. Their participants must belong to one joint witness, rather than being collected from separate alternative histories.


A split followed by a reunionORDINARY RULES
A.X
[A] B, C
[B, C] D


The first event creates B.X and C.X. The two X references share one inherited introduction. Reunion consumes B and C, reconciles the shared X once, and yields D.X.


IDENTITY ILLUSTRATION
Equal labels or the same introduction?


Where do the leftovers go?
For a joint rule such as [A, B] C, D, matching first collects the selected inputs’ unmatched remainder by introduction identity. Each output receives references to that combined remainder and fresh introductions for its explicit result. An inherited value carried to both outputs remains shared; freshly computed results remain independent.


Coexistence
[A] B, C
[B, C] D
B and C can appear together in one successor configuration. That joint availability can support the second rule.
Alternatives
[A] B
[A] C
[B, C] D
The first two rules offer competing successors. Their separate histories do not by themselves supply a configuration containing both B and C.


With several identically labeled operands, every eligible pairing can be a possibility. Adjacency in source text does not pair two calculations. Contexts and ordinary program information establish the intended association.


Can four repeated Add labels determine two intended sums?
No. They identify eligible operands, not an intended pairing. The runtime explores compatible matches. Use the language’s execution contexts or additional ordinary labels to distinguish the calculations.






04 / ABSTRACTION
Types are
computation.


An abstraction is a value reached through ordinary rules. Its derivation can reveal an application at the concrete source.


Boolean negation through a local bodyORDINARY RULES
Not.True
[True] Boolean
[False] Boolean
[Not.Boolean] (
    [True] False,
    [False] True,
)


True can derive Boolean. That evidence lets the Not rule apply to the concrete Not.True source. The body receives True, and its local rule produces False. Boolean justifies the application; it is not an extra Boolean operand appended to True.


CONCEPTUAL WALKTHROUGH
Follow evidence back to its source
This staged explanation separates what the derivation establishes from what the concrete body receives. Explore actual Rust event branches in chapter 6.


Two witnesses, one general pattern
Pair.Seed,
Pair.Other
[Seed] Intermediate
[Intermediate] Kind
[Other] Kind
[Pair.Kind, Pair.Kind] ([] Result)
Both operands establish Kind, through different derivations. The body can receive Seed and Other and introduce Result. Repeated Kind positions do not require the concrete witnesses to be equal. Two source positions still require two compatible witness coherences.


Conjunction
And.True.False.Extra
[True] Boolean
[False] Boolean
[And.Boolean.Boolean] (
    [True.True] True,
    [True.False] False,
    [False.False] False,
)
The body operates on the concrete True and False and preserves Extra as remainder. The result is False.Extra. True.False and False.True are the same particle pattern, so one rule covers both orders.


Literal outputs and scoped bodies have different transfer behavior. A literal inferred output replaces the projected concrete footprint. A body consumes exact matches and receives the remaining concrete witness. For example, with [A] B.C and [B] D, sequential execution can produce C.D, while inference can enable a direct A-to-D alternative.

05 / METAPROGRAMMING
Using rules
as values.


The language uses the same source expressions to describe rules and to manipulate whole rule values.


Produce code
Seed.A
[Seed] [A] B
Seed introduces the complete rule from A to B. Where that rule is live, it can act on A. Applying the rule reads its availability.
Replace code
([A] B).A
[[A] B] [A] C
The outer rule consumes the complete A-to-B value and produces an A-to-C value. Explicitly matching code as an operand consumes it.


Code production changes a successor configuration. It does not globally edit earlier configurations. A rule value carries its lexical capture, so moving it does not silently reinterpret it under unrelated definitions.


Local definitions and return
A scoped body has a frame with a lexical link and a return link. The lexical link tells execution where a definition comes from; the return link tells it where a body result goes. A local rule returning from its own body and an inherited rule operating within that body use those links differently.


01Match a valueAtom or whole rule
02Preserve its contextCapture and introduction
03Apply an ordinary ruleProduce a successor


Is [[A] B] [A] C a global alias?
No. It is a local consuming replacement of one rule value. The predecessor remains part of the execution graph, with its own applicable events.

06 / RUNTIME
From source
to an execution graph.


The Rust runtime parses your program and finds rules that can apply. It records each event in a graph and reuses configurations that are equivalent.


Source→Parse & lower→Match→Project & apply→Canonicalize


Parsing and lowering
Pest supplies the structural parser. Lowering interprets expressions, expands shared prefixes, and produces typed atoms and rule values. Miette reports source spans; malformed composition and resource bounds receive structured diagnostics.
Matching gates
A partial match records its actual occurrences, coherence, and frame. Compatible assignments accumulate until every input position is filled. Duplicate arrivals do not fill another slot. The gate tracks which positions are filled, not just how many arrivals it has received.
Projection and application
A relative view connects a witness to its concrete source. Projection identifies the footprint; application transfers remainder, allocates explicit results, and records the event’s dependencies.
Canonical identity
The runtime normalizes anonymous introductions and frame names while preserving sharing, multiplicity, scope, and continuations. Encountering an equivalent configuration reuses the state; additional justifications can still add support.


Pack fields with ordinary library rules


To construct an indexed field from a position and value, first load //library:position, which brings in //library:application. Then invoke its Pack operation. Packing is a standard-library computation, not a fundamental language feature or an automatic interpretation of parentheses.


With the position library loadedORDINARY RULES
Invoke.Pack.([Position] 0).([Value] 2)
This request can reach ([0] 2): one complete rule value associating position 0 with value 2. Without the library rules, the request has no built-in behavior. Pack currently supports positions 0 through 3 and values 0 through 2. It packs one field; it does not construct or validate a whole number.


You may also write ([0] 2) directly when the field is known in source. Use Pack when a computation supplies the tagged position and value. Load both application.particle and position.particle with the CLI’s --library option, or declare the Bazel dependency as shown in the position example. See the packing contract.


How the frontend expands shorthand


The lowering stage assigns executable meaning to parsed source. It currently expands A(B,C) into A.B, A.C and distributes dot composition across alternatives. This is built-in lowering behavior, not a fundamental grammar production or a transformation supplied by program rules.

    07 / MATHEMATICS
    Counting with Unit.
    

    A natural numeral is one coherence containing only independent Unit occurrences.
    

    Start with an empty particle and add one fresh Unit for each step in the count. Changing their order or renaming their anonymous introductions leaves the numeral unchanged. Each finite count therefore has one numeral class.
    

    0()
    1Unit
    2Unit.Unit
    3Unit.Unit.Unit
    

    Successor adds one fresh occurrence
    Step.Unit.Unit
[Step] Unit
    Step is consumed, the existing two Units remain, and the rule introduces one more. The result is three. Zero is (), one empty coherence; an empty file has no coherence.
    

    Membership is a derivation
    Check.Unit.Unit
[Check] Natural
[Natural.Unit] Natural
    The first rule starts the recognition process. Each remaining Unit can participate in a rule with Natural. The exact target Natural contains no unprocessed Unit or extra information.
    

    Addition is reunion
    Label two independent numeral coherences with Add. The rule consumes their labels and unites their disjoint numerical remainders.
    

    NUMERAL ILLUSTRATION
    Build a sum
    [Add, Add] ()↓
    Read the generated example

    Why the addition laws hold
    Define addition on numeral classes as disjoint union. Empty contributes no occurrences, exchanging operands changes only order, and regrouping three operands preserves all their occurrences. These give identity, commutativity, and associativity. Adding a fresh Unit commutes with that union, giving successor compatibility.
    Cancellation follows by removing the same number of indistinguishable Units from equal finite counts. The carrier’s least-closure definition supplies the mathematical induction argument. The library pairs these written arguments with finite executable checks.
    

    a + 0 = aIdentity
    a + b = b + aCommutativity
    (a + b) + c = a + (b + c)Associativity
    a + S(b) = S(a + b)Successor compatibility

    08 / COMPRESSED ARITHMETIC
    Writing numbers
    in base three.
    

    A positional ternary word uses digits 0, 1, and 2. Each position carries a power of three.
    

    The arithmetic implementation accepts natural operands up to twenty trits. A complete word includes an explicit digit at every position. Fields such as ([Digit.0] 2) preserve role, position, and value as separate concepts.
    

    REPRESENTATION LENS
    Read a number in base three
    A browser arithmetic illustration. The positional labels below correspond to the ordinary concepts used by the library, not built-in numerical literals.
    

    Write a numeral by hand
    

    Forty-seven is 1202 in base three: 27 + 18 + 2. In the sparse power library, its source is:
    

    47 · sparse power representationnumeral.particle ↗
    3^3.3^2.3^2.3^0.3^0
    

    Each occurrence contributes one power. Repetition expresses the coefficient two; the zero column needs no occurrence. The caret belongs to an ordinary atom name. The carry rules establish relationships between those names.
    

    The complete positional representation of the same number is Number.([Base] 3).([0] 2).([1] 0).([2] 2).([3] 1). These two representations are used by different library interfaces. Neither requires a decimal converter to write, and neither gives a bare 1202 atom an automatic numerical meaning.
    

    A carry is a local rewrite
    [Function.Sum.0.1.2] Return.([Digit] 0).([Carry] 1)
[Function.Multiply.2.2] Return.([Digit] 1).([Carry] 1)
    0 + 1 + 2 gives three: digit 0, carry 1. 2 × 2 gives four: digit 1, carry 1. The standalone digit library uses commutative patterns where the operation is commutative.

    Four operations, one circuit construction
    ADD
    Reduce columns
    Place both operands’ digit contributions in their columns. Combine two or three digits into one digit and a carry to the next column. The output has one extra trit.
    SUBTRACT
    Borrow, then select
    Run borrow chains in both directions. The final borrow selects the magnitude. ([Negative] 0) or ([Negative] 1) records the sign; equal operands produce positive zero.
    MULTIPLY
    Distribute and reduce
    Each pair of input digits produces a low digit in column i + j and a carry in column i + j + 1. The shared column reducer combines those contributions. Output width is twice input width.
    DIVIDE
    Advance the remainder
    Read the dividend from its most significant digit. Form three times the remainder plus the next digit. Try up to two divisor subtractions; the number accepted gives the quotient digit.
    

    Finite digit tables are repeated at the required circuit sites, whose ports preserve operation association in an orderless state. At a fixed width and operation, the rule bodies are independent of operand values. Only initial digit facts change.
    

    The generator propagates possible digit domains, omits unnecessary zero carries, and removes gates with no path to the requested outputs. Column reduction is the default layout. All generated computation executes through ordinary Photonic rules.
    

    A stream can reuse the same digit rules
    

    The streaming successor reads least-significant digits first. Carry turns 0 into 1 or 1 into 2, then switches to copying the remaining digits. 2 becomes 0 and carries onward. End is an explicit input value.
    

    [Carry.0] Copy.([Write] 1)
[Carry.1] Copy.([Write] 2)
[Carry.2] Carry.([Write] 0)
    

    Output digits are whole rule values such as [Write] 0. A meta rule consumes that message and produces Next. Twelve fixed declarations handle digit transformation, copying, acknowledgement, and completion; the input stream supplies its nested Read/Next definitions.

    09 / LIBRARY
    Build and test
    a library.
    

    The standard library is Photonic source. Bazel assembles the files; Obsidian checks their behavior.
    

    Keep roles separate from values
    

    Number.([Base] 3).([0] 2).([1] 0).([2] 2).([3] 1)
    

    This is 47. Position 0 contributes 2, position 2 contributes 18, and position 3 contributes 27. Numeric atoms are literal names. The position field establishes order; source order does not. For a local arithmetic result, ([Digit] 2).([Carry] 1) keeps each role attached to its value.
    

    Invoke a supplied function
    

    Invoke.Seed.([Function.Seed] Return.Flower)
    Invoke activates the supplied Function rule inside a scope. Its result is Flower alongside the retained callable value. Return is the implementation’s explicit completion contract.
    

    The adapter accepts user-defined inputs and results without a function registry. Compose similarly activates supplied First and Second rules in order. The nested concurrent example checks that two computations starting from Seed keep their results separate. Read the interface contract and complete examples before choosing how your functions retain or consume their code.
    

    Declare the dependency once
    

    load("//photonic:defs.bzl", "photonic_library", "photonic_binary", "photonic_test")

photonic_library(
    name = "logic",
    srcs = ["application.particle", "boolean.particle"],
)

photonic_binary(
    name = "example",
    srcs = ["request.wave", "value.particle"],
    deps = [":logic"],
)

photonic_test(
    name = "negation",
    source = "Invoke.Not.True",
    targets = ["Invoke.Not.True", "False"],
    deps = [":logic"],
)
    

    Libraries contain declarations only. Binaries combine initial coherences from their sources and load transitive libraries once per file. Tests accept literal source, file sources, or both. These mechanisms add no new language syntax or host implementation of library operations.
    

    Choose what the targets mean
    

    SettingClaim
    match = "all"Every target satisfies the expectation. This is the default.
    match = "any"At least one target satisfies the expectation.
    expect = "reached"A supported state reaches the target. This is the default.
    expect = "unreachable"Exploration closes without the target.
    

    Unknown never satisfies either expectation. Full exploration shares one graph across the target queries. Each string is a whole configuration: "A, B" requires two jointly present coherences; ["A", "B"] asks two separate questions. Reaching every listed target does not assert that all targets coexist or that no other outcomes are possible.
    

    Use path = True for direct-path reachability witnesses. Each target then receives its own path search; unreachability requires full exploration. Bazel fails inconclusive or mismatched tests and retains JSON reports for inspection.
    

    bazel test -c opt //example/library:pipeline.check
bazel test -c opt //mathematics/ternary:position.check
    

    The native pipeline forks two producer scopes, maps their results independently, and joins payloads with explicit completion evidence. Pair protocols and the finite position adapter are implemented. General Repeat, arbitrary-width native arithmetic, and generic recursive binding remain open work.

    10 / WORKSHOP
    Checking a result
    with Obsidian.
    

    Obsidian checks whether an exact target configuration can be reached from a supplied program.
    

    A target includes its complete particle contents, coherence arrangement, and sharing. This makes an arithmetic result a concrete configuration claim. The arithmetic command accepts the proposed answer and encodes it as that target.
    

    Reached
    A supported witness reaches the exact target.
    Unreachable
    Finite exhaustive exploration closed without that target.
    Unknown
    The exploration has not established a verdict. A failed direct path also reports Unknown.

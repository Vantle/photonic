Programs define their paths

Types are computation. Existing derivations enable further applications at their concrete sources. The runtime iterates these rules without a separate type-search phase or a global judgment that a program’s logic is sensible. Circular, contradictory, or later-defeated inferences must remain expressible.

When a match is discovered, eligible ancestors can gain new outgoing applications. The old history is retained; the application is an alternative at its source, not a second consumption after its successor. For decoherence, this generalizes to compatible tuples of concrete sources supported by one joint derivation.

The formal plan records the accepted source-application direction and the remaining integration gates. Resource ownership and non-monotonic support below are explicit reference proposals. They are not a claim that the complete Rust runtime is implemented.

A literal output replaces those resources and carries the unrelated remainder. One state, shared computation


A.B and B.A are the same orderless particle; A.A still contains two independent occurrences. The positive graph now interns states by current resources, ownership, scope context, and enclosing consumption. Repeated states reuse their computation: True → True becomes a self-loop. Different applications reaching the same state retain separate incoming edges. Choose an incoming application to inspect its evidence.


New evidence can still enable a rule at an existing state. “Seen” suppresses duplicate work; it does not mean no new consequences can ever be discovered. The displayed evidence path is representative; alternative derivations remain in the shared graph. Conditional invalidation is not yet integrated.


State sharing does not collapse coherence occurrences. Two equal output coherences still occupy two output positions. Equal particle storage can be shared across them, but joint interaction must preserve their occurrence histories. See the canonical-state and allocation proposal.

Candidate unchanged-remainder law: union the concrete inputs by occurrence identity, remove every directly consumed occurrence across the whole binding, and share the remainder with every output. Identity union preserves independently repeated labels. Consuming capacity is local to a coherence: two distinct compatible coherences may each explicitly consume their inherited X, while one local occurrence cannot fill two slots within its coherence. Consumption is local to this event’s result; other unselected coherences are unchanged.


This small component demonstrates literal bindings and unchanged inherited references. The output labels have explicit fresh occurrence identities for this experiment. It does not yet settle allocation for inferred outputs, changed branch resources, or conditional support.


If the two coherences independently transform inherited X into Y and Z, the preferred direction retains both as independently usable results. If both compute Y, their distinct production events give Y.Y. Common causal ancestry does not imply shared consuming capacity. The earlier single-output origin approximation needs refinement to support this direction. Inferred outputs and identity transitions still require a consistent allocation mapping; the reference components are not yet an integrated runtime.


Does broadcasting back and forth explode?


Unchanged context:

One inherited X. Return to an existing configuration.

Explicit independent branch production:
A.X → [B.X, C.X]
Each branch computes X → Y.
Reunion: A.Y.Y
Each Y computes Y → X.
Result: A.X.X


Close repeated configurations as cycles; retain genuinely new states. Unchanged inheritance must not become a Cartesian product of copies or histories. Source tuples still need one jointly compatible configuration. Sharing local state content does not authorize mixing arbitrary historical occurrences.


There is no special prohibition on bidirectional maps or broadcast cycles. The second program can double its independent resources on each round trip under the chosen branch-production semantics. Its growth is real: A.X and A.X.X are different states. Deduplication cannot remove it without changing the program. The runtime should share repeated computation and pause fairly at a budget, not mistake a budget or an already seen label for a proof that no new state exists.


See the configuration-sharing proposal for the full distinction. The positive source graph closes finite cycles today; allocation and whole-configuration memoization are still integration work.


Concrete information flows into the application


For Not.True, the True → Boolean derivation enables the Not.Boolean rule at the concrete source. Entry consumes the directly matched Not and transfers True into the body. The local True → False rule consumes that True. The enclosing application’s consumed input is recorded in the result’s source footprint, so later ancestor projection accounts for the whole computation.


For literal results, the concrete witness is consumed rather than retained beside the output. With A → B and B → A, the inferred return at A produces A, not A.A. Canonical state sharing closes that cycle. Independent equal occurrences still preserve multiplicity.


The footprint is distinct from the unrelated remainder. An evidence path may also compute X → Y, but applying B → C at concrete A.X through A → B still produces C.X. It does not carry the unrelated intermediate Y forward or consume its source X. The original source binding determines the application.


And’s abbreviated False → False branch leaves an unmatched True. The explicit True.False → False branch consumes both operands. Direct Not.True → False works normally; direct Not.True → { True → False } transfers no witness into the body. No first concept is built in as an operation marker, and no return boundary silently disposes of unused operands.


Within this fragment, returned single results carry their consumed source footprint. Across independently evolving coherences, causal support must be separated from production identity. That allocation and joint-evidence integration remain required; the origin representation here is not a universal resource algebra.


Expand source tuples, not isolated ancestors


A decoherence pattern can be discovered at two later versions. Earlier sources may also become eligible, but only through a compatible joint witness. Taking every ancestor of each input independently and forming an unrestricted Cartesian product invents combinations that the program never made jointly available.




The finite checker enumerates source frontiers and then replays a joint derivation from the bound sources. Each evidence step requires its actual prerequisites. It does not borrow an omitted resource or combine mutually exclusive consumptions. The examples use distinct coherence identities; the tuple never merges those identities merely because their histories are being inspected.


Joint siblings B and C can support a decoherence. Replacing both by their common ancestor A creates the tuple A,A, which does not supply two independent source occurrences under this consuming-input semantics. That does not make the program invalid; it means this particular application has not been enabled by those sources.


If B and C arise from competing consumptions of X, no compatible frontier contains both. If A → U and B → V each secretly need the same Ticket, separate ancestry checks are insufficient. The joint proof exposes the missing or conflicting prerequisite. Read permissions, shared context, and cross-coherence support must be explicit rather than inferred from label reachability alone.


Implementation consequence: retain the concrete source tuple, pattern-slot binding, ownership support, joint evidence, visible environments, and assumption dependencies. Rediscovering equivalent evidence does not duplicate an application. Distinct bindings and program-defined alternatives remain distinguishable. The finite checker does not yet allocate outputs or resolve ambiguous support mappings for arbitrary many-to-many hyperedges.


Circular and invalidated inferences remain programs


The relevant concepts are non-monotonic reasoning and cycles through negation. An inference may depend on a match being absent, and later information can defeat that support. The runtime should represent the dependency and its changes instead of refusing the program or silently treating an early failure to find a match as permanent absence.


Well-founded semantics provides a useful comparison with true, false, and undefined answers and explicit conditional dependencies. It can leave circular answers unresolved while still describing unaffected conclusions. This is research precedent, not a requirement that every Molten program conform to a particular logic. This panel exhaustively checks stable interpretations of tiny finite ground normal programs and computes their alternating fixed-point approximation. The notation absent(Q) is explanatory; it is not the Boolean Not operation or committed Molten syntax. The panel is a semantic comparison, not a proposed separate type phase or a universal program-validity test.


Mutual negative dependencies can have several interpretations. A self-negating dependency can have no stable interpretation while still retaining a meaningful unresolved dependency graph. Independent support matters: adding Q can defeat the default justification for P without defeating an independent fact P. Contradictory asserted labels can also coexist without the evaluator inventing every unrelated proposition.


Proposed runtime representation: retain every derivation’s supporting evidence and its absence assumptions, qualified by scope, input binding, and revision. Later changes can defeat one justification, preserve another, or leave alternatives unresolved. Append the change to the derivation history; do not erase the fact that a conditional derivation was made. Incremental tabling offers a concrete precedent for tracking changes to dependencies. SWI-Prolog: Incremental tabling.


An assumption alternative is not automatically another coherence. Coherences are independently evolving contexts; possible interpretations describe which assumptions can hold across those contexts. This distinction preserves the parallel-context contract.


Completeness means enabling the defined possibilities


The runtime is not a judge of program intent. Its obligation is to apply the language’s precise rules, retain the information needed to explain applications, and avoid silently discarding alternatives. Inconsistency, cycles, and invalidation are behaviors to represent. A missing premise means that particular application is not enabled; it is not a declaration that the whole program is invalid.


There is no semantic maximum derivation depth. Any finite derivation should remain discoverable under a fair, sufficiently resourced run. Infinite branching requires fair enumeration as well as fair event scheduling. A finite budget reports a pause, not logical falsity or permanent absence.


Completeness must be stated relative to a semantics. The finite negative-program panel can enumerate all stable interpretations of its small input. An unrestricted runtime cannot promise a terminating decision about every unbounded absence question. It can preserve conditional results, explore alternatives fairly, and expose incomplete work without choosing an answer arbitrarily.


Logical inconsistency and resource identity are separate questions. Allowing a program to assert opposing information does not make two references into two physical inputs. Conversely, ownership rules must not be used as an excuse to forbid explicit production or sharing that the language has defined.


Implementation gates


  1. Keep one iterative event mechanism. Existing evidence awakens newly enabled concrete-source applications, including eligible ancestor tuples.
  2. Specify ownership projection and output allocation, then integrate joint evidence across coherences. Preserve independent sources and shared origins without accidental duplication.
  3. Define absence scope and assumption behavior. Represent conditional, defeated, and conflicting support without a global program-validity gate.
  4. Build a fair dependency agenda with resumable budgets. Revisit sources when evidence changes; record equivalent bindings once while retaining their alternative justifications.
  5. Lower a small source subset into this representation. Abstraction remains ordinary rules; diagnostic errors distinguish unsupported syntax from meaningful but unresolved computation.
  6. Compare optimized execution with finite exhaustive references, then measure candidate visits, support growth, allocations, and event throughput.


The formal plan separates accepted commitments from open allocation and absence policies. The current Rust kernel is still a literal multiset primitive. The executable reference components here are intentionally scoped: source inference with single-output ownership, finite consuming coherence tuples, finite absence semantics, and literal remainder broadcasting with branch production. Their integration remains required work.

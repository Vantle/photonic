# Structural construction reference

The independent Rust model in [model/](../model/model.rs) begins the executable semantic work required by [dynamic.md](dynamic.md) and the [recursive value contract](collection.md). It has no production frontend, matching, storage or proof-engine dependency. Build and run it through the pinned Bazel toolchain:

```sh
bazel test -c opt //model:test
bazel test -c opt //model:conformance
```

## Structural boundary

The model distinguishes Value, Particle, Input, Destination, Output, Body and Rule. Particles, inputs, outputs and bodies canonicalize their unordered contents while retaining multiplicity. An input containing one empty particle differs from an empty input. An empty output differs from one empty destination, and an absent body differs from a present empty body. Types prevent an input configuration from being substituted directly into a value position.

A contextual Rule names its lexical context. Nested rule values and bodies retain their own context references. Concrete contexts are nominal identities supplied by the model fixture; equal syntax in two distinct contexts remains different code. Deferred declarations additionally distinguish locally bound contexts from captured identities, as described below. Canonicalizing concrete context graphs under administrative renaming remains open.

Fragment carries immutable structural content and evidence. Its constructor is private to the model. Inspection of a concrete occurrence adds its read identity and reachable contextual dependencies. The construction API creates typed composites from fragments, unions their dependencies and preserves nested captures. Repeated code description insertion may duplicate syntax positions but retains the same read identity; it does not produce or transfer an additional live resource.

Opening a rule returns its input and output fragments plus a private origin. Closing that inspection reconstructs the original lexical context. Even replacing both visible components retains the origin's read and history dependencies. Constructing a new outer rule instead uses the construction context. These are different operations, including when their output text would look the same.

## History assumption

The first model uses explicit finite branch assignments. A history maps each named fork to one alternative. A construction may use a source only when its current history includes every source assignment with the same alternative. A missing assignment is insufficient evidence, and a different assignment is a conflict. Extending an assignment is immutable and rejects attempts to replace an existing alternative.

This is an explicit restricted compatibility model, not an implementation of Photonic's full source inference or grounded proof support. Configuration checks reject duplicate identities within a particle, inconsistent shared occurrences, dangling context references and inadmissible occurrence histories. The fixture still supplies the underlying identities, context graph and branch assignments; these checks do not validate arbitrary external proofs. Deriving assignments from production events, checking competing event histories, deriving general proof support and admitting historical construction witnesses remain separate work. Checked finite projection and capture import are described below.

Evidence retains each inspected occurrence's identity, complete value and history, plus contextual dependencies and the current branch assignment. Its read-ID view is derived from those witnesses. Combining evidence rejects inconsistent descriptions of one occurrence, including during quotation and suspended construction. It intentionally retains conservative dependencies rather than minimizing them. Rule reconstruction must not erase a dependency just because a source component becomes empty or is replaced. Unknown atoms remain literals; there is no spelling convention that turns them into variables.

## Tested laws

The first suite checks arbitrary role/payload spelling, construction from inspected role and nested-rule payload occurrences, exact reconstruction through depth 16, distinct empty forms, permutation and multiplicity, mixed contextual insertion, body origins, output replacement and retention of a private origin when both components are replaced. A 729-pair history matrix independently checks assignment inclusion and inspection admission. Host-driven structural construction exercises depths 0, 1, 2, 3, 8, 16 and 32.

Host-driven generation demonstrates that the model representation can grow new structures. The staged model below additionally represents and evaluates generator factories. Neither establishes native structural execution, a runtime-recursive Photonic generator or a collection library. The construction operations remain atomic reference primitives; the machine below adds resumable template traversal. No universal preservation proof is claimed from finite tests.

## Binding and templates

Scope allocates typed slots with a nominal lexical owner and a unique position within that scope. Literal atoms never become references by convention. Binding stores immutable fragments under slots of one structural sort; immutable nested environments retain access to ancestor slots, reject attempts to bind an ancestor from a child, and reject reuse of an active scope identity. Rebinding an occupied slot is an error. A reference to a missing slot or inaccessible scope produces a structured failure.

Templates distinguish literal construction from references at each supported sort: value, particle, input, output and body. Building ordinary rule structure uses the current construction context. Building a body introduces a fresh local context binder for its declarations; activation supplies that binder's concrete frame. Substituting a captured fragment retains its original context and evidence at every sort. Every reference is checked against the current construction history before insertion. Sealing rejects unbound local references before publishing executable code.

The template suite checks unknown roles and contextual payloads, administrative renaming of binder scope identities, ancestor access and child isolation, duplicate binding rejection, missing external references, all supported structural sorts, body capture retention and history rejection on substitution. Repeated substitution preserves syntax multiplicity without manufacturing distinct source reads. One fixed template wraps increasing depth through 32 host-driven instantiations.

## Generated bindings

The staged construction model represents a generator as a declaration of future typed parameters and a term. A term either builds a closed value or quotes another generator definition. Parameter declarations support all five binding sorts, reject duplicate positions and foreign owners, and preserve literal atom semantics. Quotation validates references through every nested definition: references owned by an enclosing future declaration may remain unresolved; every external reference must resolve in the captured environment and pass the current history check. A reference with an undeclared position is rejected even when its owner is a known future scope.

A closed generator captures an immutable environment and the evidence needed by its external references. Application supplies exactly the declared parameters with their exact sorts in a private nested environment. All argument and generator dependencies are retained, including for an argument the body does not use. A quoted child captures its parent's now-bound parameters while retaining its own unfilled future parameters. Separate invocations of one factory can therefore produce separate builders without exchanging bindings, histories or payload captures.

The factory test represents a generator whose role parameter becomes the input of a generated field builder. The returned builder owns a new payload parameter; applying it creates ordinary closed rule structure. Two invocations retain different roles, while a nested rule payload retains its own lexical context and source identity. Further tests cover binder renaming, missing external and undeclared local references, duplicate/foreign/mismatched declarations, all parameter sorts, arity, ancestor histories, nested capture evidence and inactive future evidence at quotation time.

Generator products belong to the reference construction machinery, not to live Photonic configurations. This is a staged semantic experiment with explicit quoted definitions, not production syntax or a second native callable value kind. Scope identities in fixtures are nominal; invocation behavior is tested under their renaming, while canonical equality of quoted code remains unimplemented. The application model below supplies direct matching, ownership and fresh declaration binding, including construction through typed templates. Connecting generator evidence to live introduction and projecting inferred witnesses remain integration gates.

## Concrete application

Configuration holds worlds, frames, a distinguished retained root and one compatible history. A request names executable code and explicitly selects the occurrence identities for each input particle. It is a direct application checker, not a search engine. Selected worlds must be distinct and share an execution frame. Values match exact closed structure, including nominal captures. Within a particle, positions require distinct occurrences. Across distinct worlds, a joint match may select the same shared introduction; consuming it does not create independent resources.

A live rule must occur in a participating world and contributes an executable read. A declaration must be visible through the execution frame's lexical chain; a parent return link does not grant lexical visibility. Lookup terminates even on a cyclic fixture graph. A declaration's return owner is its containing frame, while a live closed rule retains its captured owner. Applying code owned by the current child frame returns to that frame's parent. Inherited code continues in the current frame.

Application removes consumed introductions from participating worlds, unions the remaining occurrences by identity and gives each output the same shared remainder. Explicit output positions receive fresh occurrence identities, including equal sibling outputs. Untouched worlds retain their contents. Each event records reads, consumed places and resource, world and frame maps. Fresh resource flow depends on consumption and any held returning resources; executable reads remain separate support. A body enters a fresh frame with its declared lexical context and reserved consumption. Closed nested values keep their own captures. Reachability retains captured frames and follows parent, lexical, declaration and held-value dependencies; unreachable frames and their target flow entries are reclaimed. Allocation remains fresh along a configuration lineage after reclamation and reports checked exhaustion only when allocation is required.

The declaration representation separates return ownership from embedded captures. Ordinary executable structures use concrete context identities. The same structural constructors can represent deferred declarations with context references: Captured retains an existing identity, while Local names an enclosing body binder by depth. Local(0) denotes the nearest body activation. A nested body's declarations introduce another binder; its lexical context expression belongs to the surrounding scope. Local references are typed separately from executable identities.

Body.bind validates every local reference before sealing a contextual body. An out-of-scope reference fails with a structured depth error. On activation, the body's binder resolves to the newly allocated frame. References to it inside deeper bodies become captured identities, while references to those bodies' own future binders remain deferred. Particles, inputs, outputs and nested declarations are sorted after substitution. Captured references remain unchanged, including when their numeric identity happens to equal a newly chosen owner. Body.new embeds already closed declarations; activation.capture embeds closed rule structure without making its captures local.

These operations give a compositional substitution rule: replacing a particular body binder changes only references to that binder. Descending into a nested body increases the binder depth; descending into ordinary nested rule values does not. Sealing checks that every local reference has a corresponding binder, and activation produces executable structures with concrete contexts at the active level. The preservation argument still needs integration with construction evidence and source-inferred projection; no general production simulation is claimed.

Seven activation tests cover fresh versus captured contexts, nested outer references, imported bodies, invalid depths, context evidence and reconstruction, depth families through 32, and actual execution of locally emitted and imported closures with different lexical results. The depth family also checks that embedding and reactivating closed code preserves its structure at every level. A native comparison imports a ground source fixture into the reference representation: a local declaration emits code, returns, and later calls that code through its retained local frame. The result selects the local A declaration despite a competing root A declaration. The test adapter shares the frontend's parsed source representation, but does not use the native matching or rewrite implementation to derive the reference result.

Construction now supports typed deferred fragments while retaining its private evidence origin. Deferring ordinary construction captures its current context; entering local declaration construction changes the syntactic binder without discarding that origin. Lifting an inserted closed fragment preserves all captures, reads and history dependencies. Sealing returns a closed structural sort only after checking binder scope. A local rule fragment cannot be sealed directly as executable code; it must occur beneath its body binder. The explicit closed-declaration body constructor still embeds already captured definitions, while template Body.Build creates local declarations.

Six declaration integration tests compare recursive and resumable construction with evidence retained. A mixed local/imported closure fixture resumes at every suspension boundary, checks its introduction against the original live witnesses, activates and executes both closures, and checks their different lexical results. Further tests cover missing bindings and competing histories at every suspension boundary, all five inserted fragment sorts inside local declarations, refusal to publish an unbound local rule, generator invocation, and nested body construction and activation through depth 32. The native escaped-code comparison checks both direct structural import and templates constructed one machine step at a time. Introduction has the concrete admission boundary below; inferred and historical witnesses still need their own law. Activation, capture conversion and sealing remain atomic reference operations.

Thirteen application tests cover exact matching, multiplicity, shared and fresh ownership, code locality, empty inputs, scoped reservation and return, lexical visibility, captured owner behavior, historical results after code consumption, invalid configurations, capacity and repeated reclamation. Their raw configuration fixtures isolate application semantics. The declaration integration tests additionally use checked construction introduction. Application itself is atomic and has no production work-accounting claim.

The separate conformance target depends on the native engine; the model library does not. A 27-case matrix varies consumed multiplicity, output branching and retained multiplicity, comparing output values and occurrence sharing with direct native execution. Further cases cover a live executable read, a joint match consuming one introduction shared across worlds, a scoped declaration return and escaped local code. The matrix also checks that a shared remainder does not satisfy a complete target requiring distinct fresh copies. An additional scoped-return case compares complete composed resource, world and frame maps with a supported native view. These are restricted ground comparisons, not arbitrary contextual graph equivalence, general flow-map conformance or source-inference preservation.

## Introduction and flow

The [introduction operation](../model/introduction.rs) publishes one completed fragment into one concrete world. It checks the configuration's history against the fragment, requires every recorded contextual dependency to exist, and compares every read witness with its complete live occurrence in that world. Matching an ID alone is insufficient. Consumption is explicit, requires distinct existing occurrences and may overlap reads. The operation gives the new value a fresh identity, preserves the unconsumed remainder and captured code contexts, and records reads, consumption, contextual support and flow. Capacity or admission failure leaves the source configuration unchanged.

Introduction is a reference construction transition, not an ordinary rule firing or new native syntax. It creates a fresh occurrence of completed code description; it does not silently transfer an existing occurrence's identity. Its resource flow follows explicit consumption, while inspected code and data remain separate read support. The selected world supplies a context dependency even when both reads and consumption are empty. A later application can read the introduced code and consume its arguments through the ordinary application model.

This first introduction boundary requires live witnesses in the selected world. It does not yet admit witnesses available only through another coherence, held resources, an earlier supported event or source inference. An already introduced result survives later consumption of its source reads, but reintroducing a retained fragment after those reads disappear requires evidence that this operation cannot yet establish. Configuration contexts and branch assignments remain nominal fixtures; the model is not an external proof checker or a proof that arbitrary construction programs followed the intended operations.

The independent [flow implementation](../model/flow.rs) constructs identity maps, validates exact target domains and existing source references, projects a selected resource basis, and composes resource/world relations and optional frame origins. An absent frame origin stays absent through composition. Missing intermediate entries produce structured failures rather than silently dropping dependencies. Domain validation checks map shape, not the semantic justification of its edges. Resource projection alone is not inferred matching: it neither establishes exact consumption nor carries all event read support. A composed resource map cannot replace the supporting event chain.

Four flow tests include all 4,096 triples of two-by-two resource/world relations and all 729 triples of two-frame optional origin maps. Independent path enumeration checks the result; associativity, identity, empty-world context retention and malformed-map rejection are also covered. A native scoped-return fixture checks that held consumption composes back to its original resource while an unrelated remainder retains identity. Six introduction tests cover construction followed by execution, read/consume overlap, empty consumption, witness mismatch, conflicting evidence, history/context admission and allocation failure. Conflicting evidence is additionally checked across every construction suspension boundary and at quotation. The mixed-capture integration fixture uses checked introduction after every construction suspension boundary.

## Resumable construction

Machine interprets a template through an explicit task stack, visiting one child at a time and retaining private partial composites. Each task transition consumes one model work unit. `run(0)` leaves unfinished construction unchanged. Entering a declaration body saves the enclosing construction context; completing that body restores it before assembly continues. A successful result is published only after the complete outer value is assembled and sealed; a failure is terminal and discards partial work. Further calls after either outcome preserve the outcome and consume no additional work. Borrowed immutable templates and environments, an immutable sealing context and private deferred construction state prevent external mutation beneath a suspended cursor.

The recursive template interpreter remains the independent traversal oracle. Machine tests compare both success and structured failure at every single suspension boundary for empty shapes, nested code, branching particles, bodies, references and missing or incompatible bindings. They also compare repeated budgets of 1, 2, 3, 7 and 32 work units and repeated observation after completion.

These work units specify reference-machine progress, not production runtime step accounting. Fragment cloning, dependency union, multiset sorting, capture conversion and final sealing still occur within individual primitives. Final sealing traverses the assembled structure atomically. Consequently this is cooperative resumability between structural operations, not a wall-clock preemption or hard-memory guarantee. Native integration must separately account for those primitive costs, code/environment limits and production observation compatibility.

An invocation that produces a closed value uses the same machine and retains generator and argument support in its final result. Suspension-prefix tests compare this path with direct invocation, including unused-argument evidence. Quotation validation and parameter preparation remain atomic reference operations; the machine API explicitly rejects a quoted-generator term rather than pretending its validation has been budgeted. Resumable quotation is still required before production integration.

## Checked paths and projected bindings

[Path](../model/path.rs) starts from a valid fixture configuration and replays explicit application or introduction requests. Each extension reruns the corresponding semantic operation, checks its flow endpoints and composes the accumulated flow. Its states, records and composed map are immutable to callers. A record preserves its request, immediate flow, reads, consumption and contextual support; record position identifies its source and target states. Projection accepts this checked path rather than an arbitrary caller-supplied flow. The initial configuration remains a premise, and finite reference replay is not a general external proof checker.

[Projection](../model/projection.rs) first validates a concrete match at the path endpoint. A local executable must occur in a participating endpoint world. A declaration belongs to the source state and must be lexically visible at the projected execution frame; captured input values are mapped into the witness context before matching. Distinct input particles require distinct witness worlds even when their origins project to one source world. The selected endpoint frame must have a source origin, every contributing source world must belong to that source frame, and a consuming footprint that reaches a held place is rejected under the current native projection contract.

The binding separately records the broader footprint, exact sources and executable reads. Every selected witness contributes its consuming basis to the footprint. A source is exact only when that basis is one ordinary source occurrence and its complete value agrees after capture mapping. A freshly regenerated equal value can therefore be exact, while a differently captured value is not. A generated executable contributes the basis of its read occurrence, independently of argument consumption. Its captured owner may have no source-frame origin; the binding preserves that fact for capture import rather than substituting a root owner.

For `Seed.A [Seed] [A] B`, matching the generated code on A projects consumption to A and executable reads to Seed. Earlier reads used to produce that code remain in the checked path. Two paths can have identical endpoint states and resource maps while retaining different read support, so the projected binding alone cannot replace the path. The Projection object keeps an immutable reference to that path and its concrete request.

Eight tests cover replay and failed extension, seedless requests, exact versus derived values, differing captures, retained reads despite equal flows, checked introduction in a path, held-footprint rejection, unmapped execution frames, source-frame disagreement and empty input. Three native test families add six cases comparing supported event footprints, exact sources and reads: changed derivations, equal regeneration, two witness worlds from one source world, multi-resource production, generated code and an escaped owner requiring import.

## Projected application and capture import

Projection now applies its checked binding to the source configuration through the same [rewrite operation](../model/rewrite.rs) used by direct application. Each ordinary destination removes the broader consuming footprint; each destination with a body removes only exact sources and reserves those sources with any held resources consumed by a return. Mixed scoped and ordinary destinations therefore compute their own remainders. Explicit output values depend on the broader footprint plus return consumption. Executable reads remain separate support. Untouched worlds, shared remainders and fresh output identities retain their existing contracts.

The [import operation](../model/import.rs) discovers the complete captured graph needed by executable code, allocates every new frame before reconstructing edges, and remaps captured references inside inputs, outputs and deferred declarations. It preserves local binders. Existing frame origins reuse the source environment; absent origins receive fresh identities. Discovery includes imported declarations, lexical and return parents, and held values. A mapped outer code owner does not excuse importing an embedded unmapped capture. The resulting rewrite reclaims frames unreachable from the result and validates its flow endpoints.

Held import preserves a source occurrence identity when a singleton basis carries the same complete value, mapped captures and history. Other held values receive fresh identities, shared consistently across imported frames. If several held witnesses map to the same source occurrence, import retains one occurrence and unions their flow bases. The regression fixture `A.Call [A] A.A [A.A] (Make [Make] [Call] [Payload] Result)` exercises that convergence through a checked reference path. Reconstructed configurations must still satisfy the original occurrence-identity invariant.

This investigation found the same duplicate-identity defect in the native import primitive. Its old implementation appended both remapped held tokens and allowed the final flow map to overwrite one basis. [The native regression](../language/test/import.rs) supplies two held witnesses of one source occurrence shared across two worlds: the corrected import retains one token and both source places. This is an intentional correctness correction to held import, not a runtime speed claim. The fixture tests the application primitive; bounded native exhaustive exploration of the growing reference program above did not reach the corresponding event and is not reported as end-to-end native validation of that program.

Two new core test families cover mixed scoped/ordinary consumption, repeatable immutable application, exact versus derived held identity, imported declaration graphs and a mapped outer owner containing an unmapped capture. The six existing native projection cases now also compare resulting particle values, occurrence sharing and complete scalar resource/world/frame flow. Two scoped cases compare held counts, frame parents, lexical links and complete flow. An escaped-code case checks the inferred result and execution through the imported local declaration to Done. These are restricted observations; they do not establish arbitrary contextual graph equivalence or general structural conformance.

Paths currently contain direct application and introduction steps only. A projected Event does not embed its supporting path; retain the Projection when that evidence is needed. Next represent inferred steps together with their auxiliary derivations, then admit justified historical construction witnesses. General inferred-event replay, historical admission, cyclic proof support and the full structural commuting law remain open. Replay, projection, capture import and rewriting are atomic reference operations with no production budget-accounting claim.

## Verification

The model passes 78 tests through `bazel test -c opt //model:test`, including the history and flow matrices, suspension-prefix comparisons, construction/activation depth families and checked projection cases. Twelve conformance tests exercise 41 native comparison cases plus the reference held-convergence fixture through `bazel test -c opt //model:conformance`; escaped local code additionally compares direct import with resumable template construction. Both targets and the 208-test native unit suite ran freshly during this increment. The build runs Rustfmt, Clippy and Bazel checks. The subsequent `bazel test -c opt //...` passes all 109 targets: 103 execute freshly and six use valid cached results, including the historical differential harness and browser/WebAssembly ground conformance. This is local native build evidence, not a new cross-platform run, a benchmark, or native/WebAssembly structural conformance.
